## Why (2-paragraph context)

After F5.1 P1a (`fb99b74`) and P1b+P1c (`72a1b47`) the password-auth
backend is consolidated to one router (`src/routes/auth.js`), feature-
parity with the deleted shadows, audit-log-complete for the
`user_register → user_login → user_logout` lifecycle, and free of dead
`global.sessions` machinery. But the dashboard still has zero password
input fields — `LogIn.jsx` and `SignUp.jsx` only render OAuth buttons —
so users who hit a Google-consent failure are locked out. F5.2 closes
that loop end-to-end: forgot-password and change-password flows on the
backend, then surfaces them (plus sign-up and sign-in) in the UI.

In parallel, F5.1's verification matrix surfaced a UX-relevant audit-
log issue: a single dashboard page-load triggers ~6–10 read endpoints
plus one `token_validated` row per authenticated request, producing
20+ rows of "background activity" the user never performed.  Because
F5.2 P3.4 will eventually surface the activity log to end users in
account/security settings, we have to clean those emit sites BEFORE
the UI lands — otherwise we'd ship noise as a feature.

## Phase 1 — Password reset flow

**Goal.** Forgot-password works end-to-end, backend only.  UI in P3.3.

### Schema migration (in `src/database.js`, via `safeMigration`)

```sql
CREATE TABLE IF NOT EXISTS password_reset_tokens (
  id           TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL,
  token_hash   TEXT NOT NULL,            -- bcrypt(rawToken)
  expires_at   TEXT NOT NULL,            -- ISO timestamp, +2h from create per D3
  consumed_at  TEXT,                     -- ISO timestamp, null if unused
  request_ip   TEXT,                     -- forensics on link issuance
  created_at   TEXT NOT NULL,
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_password_reset_tokens_user_id ON password_reset_tokens(user_id);
CREATE INDEX IF NOT EXISTS idx_password_reset_tokens_expires_at ON password_reset_tokens(expires_at);
```

### Endpoints (in `src/routes/auth.js`)

#### `POST /api/v1/auth/password/reset/request`

- Body: `{ email }`.
- **Always** returns 202 — never leak whether the email exists.
- If user exists:
  - Mint random 32-byte token (`crypto.randomBytes(32).toString('hex')`).
  - Insert `password_reset_tokens` row with `bcrypt.hash(rawToken, 10)`,
    `expires_at = now + 2h`, `request_ip = req.ip`.
  - Send email via `emailService.sendPasswordResetEmail(email,
    resetLink)` where `resetLink = ${PUBLIC_URL}/reset-password?token=${rawToken}`.
- Rate limit:
  - Per-IP: existing `authRateLimit` (already on the router).
  - Per-email: 3 / hour (new — small in-memory map keyed on
    sha256(email).slice(0,16); hour-rolling window).
- Audit emit: `password_reset_requested` with
  `details: { email_known: bool, ip }`.  No raw email in details.
- Logger: `[Auth/PasswordReset] request received { ip, email_known }`.
- Timing-safe: if user not found, still do a `bcrypt.hash` of a
  throwaway value to keep response time within ±50ms of the
  user-found path.

#### `POST /api/v1/auth/password/reset/confirm`

- Body: `{ token, newPassword }`.
- Lookup all unconsumed, unexpired rows; for each row, attempt
  `bcrypt.compare(rawToken, row.token_hash)`.  First match wins.
- Reject:
  - No match → 410 GONE `{ error: 'INVALID_OR_EXPIRED_TOKEN' }`.
  - `consumed_at` already set → 410 GONE same code.
  - `expires_at < now` → 410 GONE same code.
  - `newPassword` fails existing `isStrongPassword` → 400.
- On success:
  - `UPDATE users SET password_hash = bcrypt(newPassword, 12)
    WHERE id = ?` (cost 12 — bcrypt 14 deferred to F5.3).
  - `UPDATE password_reset_tokens SET consumed_at = now WHERE id = ?`.
  - Call `revokeAllUserSessions(userId)` from
    `src/lib/authHardening.js` so prior cookies are dead.
  - Establish a new session for the user (`req.session.user = …`),
    matching the `/login` shape so the UI can redirect to
    `/dashboard/` already signed in.
- Audit emit: `password_reset_completed` with `details: { sid }`.
- Logger: `[Auth/PasswordReset] confirmed { userId, sid }`.

### Email integration

- `emailService.sendPasswordResetEmail(to, link)` — new method in
  `src/services/emailService.js`.  Uses the same transport as the
  welcome email.  Subject: "Reset your MyApi password".  Body:
  link + "this link expires in 2 hours" + "if you didn't request
  this, ignore this email".

### Tests (`f5-2-p1-password-reset.test.js`)

1. Request for known email → 202 + `emailService` mock called once
   with the correct address + token UUID.
2. Request for unknown email → 202 + `emailService` mock NOT called
   + response time within ±50ms of test 1 (timing-safe).
3. Confirm with valid token → 200, `users.password_hash` updated,
   `password_reset_tokens.consumed_at` populated.
4. Confirm with consumed token → 410 INVALID_OR_EXPIRED_TOKEN.
5. Confirm with token whose `expires_at` is in the past → 410.
6. Confirm with garbage token (no row matches) → 410.
7. Confirm with valid token but weak `newPassword` → 400 + token NOT
   consumed (so the user can retry without re-requesting).
8. After successful confirm, prior session cookie returns 401 on
   `/me`.
9. Per-email rate limit: 4th request to same email within an hour →
   429.  3rd request still 202.
10. Per-IP rate limit (relies on existing `authRateLimit`): 1000th
    request from the same IP → 429.
11. Audit rows present at each branch with the right action.
12. SQL injection / token-collision smoke: token whose hash collides
    with another user's hash on the first 32 bits is rejected (we
    `bcrypt.compare` against every candidate, not LIKE-match).

**Commit message.**
`feat(auth): F5.2 P1 — password reset request + confirm endpoints`.

## Phase 2 — Change password + session revocation

**Goal.** Authenticated user rotates their password without logging
out of the active tab; every other device they were signed into is
revoked.

### Endpoint (in `src/routes/auth.js`)

#### `POST /api/v1/auth/password/change`

- Auth: session-authed (cookie) OR Bearer (master token).
- CSRF-guarded for session-authed callers via `requireCsrfForSession`.
- Body: `{ currentPassword, newPassword }`.
- Validate:
  - `currentPassword` matches `users.password_hash` via
    `bcrypt.compare` → 401 `INVALID_CREDENTIALS` on mismatch.
  - `newPassword !== currentPassword` (cheap string compare AND
    bcrypt re-compare for safety) → 400 `PASSWORD_REUSED`.
  - `newPassword` passes existing `isStrongPassword` → 400 on fail.
- Mutate:
  - `UPDATE users SET password_hash = bcrypt(newPassword, 12)`.
  - For session-authed callers: revoke all OTHER sessions for the
    user via `revokeAllUserSessions(userId, { except: req.sessionID })`
    (new `except` parameter on the existing `authHardening.js` helper).
  - For Bearer-authed callers: revoke ALL sessions (no current
    session to preserve).
- Notification email (D2):
  `emailService.sendPasswordChangedNotification(user.email)` — fire-
  and-forget; failure logs but doesn't block the 200.
- Audit emit: `password_changed` with `details: { sessions_revoked: N,
  via: 'session' | 'bearer' }`.
- Logger: `[Auth/PasswordChange] success { userId, sessions_revoked }`.

### Tests (`f5-2-p2-password-change.test.js`)

1. Wrong `currentPassword` → 401 `INVALID_CREDENTIALS` + no DB write.
2. `newPassword === currentPassword` → 400 `PASSWORD_REUSED` + no DB
   write.
3. Weak `newPassword` (length / class) → 400 + no DB write.
4. Valid → 200, `users.password_hash` changed, current session still
   200 on `/me`.
5. After successful change, ANOTHER session for the same user (a
   second `request.agent` that logged in earlier) → 401 on `/me`.
6. CSRF gate: change without `X-CSRF-Token` header → 403.
7. Audit row present with correct `details.sessions_revoked` count
   and `details.via` field.
8. Notification-email mock called once with user's email.
9. Bearer-auth path: change via master token → 200 + ALL sessions
   for that user revoked + audit `details.via: 'bearer'`.

**Commit message.**
`feat(auth): F5.2 P2 — change password + revoke other sessions + email`.

## Acceptance criteria for the milestone

- A user with no prior account can:
  1. Open the dashboard, sign up with email+password+terms — get
     auto-logged-in.
  2. Log out, then log back in with email+password.
  3. Log out, click "Forgot password?", receive an email, click the
     link, set a new password, end up logged in on the dashboard.
  4. Open account settings, change their password (with current-
